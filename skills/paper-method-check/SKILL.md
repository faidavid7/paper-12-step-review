# 方法深度與合理性

先讀 `../paper-review-shared/conventions.md`，執行其中的「開始前」。問題編號用 P4-x。

## 缺少上游產出時
- 需要 `issues.json` 的 `handoff.deficits`（來自 paper-survey-and-naive-ideas）。
- 不存在時，從論文的 introduction 與 related work 整理論文自己宣稱的不足，編號 D1…Dn，標示「來源：論文自述，未做 survey」。在「範圍與限制」說明：沒有獨立 survey，可能漏掉論文沒提的不足。

## 檢查

### 1. 資料流
- 描述 inference pipeline 與 training pipeline。每個階段寫出 input、運算、output 與 tensor 維度。
- 標出 training 與 inference 不一致的地方，例如只在 training 使用的資訊。檢查有沒有資訊洩漏。

### 2. 合理性：每個設計決策
為每個 block 或 function 編號 M1、M2⋯，逐一檢查：
- 動機：為什麼需要它？對應哪個不足 D？
- 數學依據：有沒有推導？依共用規範的「驗證守則」逐步重推。
- 更簡單的替代：換成更簡單的設計（刪除、換成標準元件、固定參數）會怎樣？論文有沒有說明或實驗？
- 假設：這個設計依賴哪些假設？假設在論文的 setting 中是否成立？
- 成本：增加多少參數、計算量或記憶體？論文是否報告？

### 3. 深度
- 核心機制：用 1–2 句寫出方法真正新的機制。寫不出來時，列為 Major。
- 判斷方法屬於以下哪一種，並說明依據：
  - 有新機制，並有理論或分析支撐。
  - 有新機制，只有實驗支撐。
  - 既有元件的組合，組合帶來非顯而易見的效果。
  - 既有元件的組合，效果可以預期（工程堆疊）。
- 有沒有 trivial 的部分被包裝成貢獻？
- 有沒有關鍵部分被一筆帶過，例如沒有說明的超參數、沒有解釋的 trick？

### 4. 不足的覆蓋
- 表格：不足 D、負責解決的設計決策 M、機制說明、是否合理。
- 沒有任何 M 對應的 D，而論文宣稱要解決它時，列為 Fatal 或 Major。

### 5. 預期結果
- 依方法的機制，寫出應該觀察到的實驗結果，編號 X1、X2⋯。例如「若 M2 有效，長序列上的提升應大於短序列」。
- 每項標出它檢驗的 M。
- 寫入 `issues.json` 的 `handoff.expected_results`。設計決策寫入 `handoff.design_decisions`。

### 6. 論文類型與理論基礎
- 判斷論文類型：方法、理論或應用。說明依據。
  - 方法論文：方法設計是否有動機，實驗是否證明方法有效。
  - 理論論文：定理與證明是否正確，假設是否合理。
  - 應用論文：問題是否真實存在，方法是否適合該應用，評估是否貼近實際情境。
- 理論基礎：
  - 問題是否有數學 formulation（目標函數、假設、符號定義）？
  - 方法是否有理論支持，例如收斂性、界限或與既有理論的連結？
  - 沒有理論時，論文是否用足夠的實證分析彌補？
  - 依論文類型判斷是否足夠。理論論文的要求最高，應用論文的要求最低。

## 輸出
- 報告 `paper-method-check_<zh 或 en>.md`，依共用規範的「每份報告的固定結構」撰寫：
  1. 結論：方法是否合理、深度屬於哪一種。
  2. Pipeline 描述。
  3. 設計決策表（M、block、動機、對應 D、數學依據、更簡單的替代、假設、疑點）。
  4. 數學驗證結果：每個推導寫「正確／有誤／待確認」與理由。
  5. 深度判斷。
  6. 不足覆蓋表。
  7. 預期結果 X1…Xn。
  8. 論文類型與理論基礎評估。
  9. 問題表（P4-x）。
  10. 交接：M 與 X 清單（給 paper-experiment-check）；核心機制（給 paper-novelty-positioning）。
  11. 範圍與限制。
- 把 P4-x 與 `handoff.design_decisions`、`handoff.expected_results` 寫入 `issues.json`。
